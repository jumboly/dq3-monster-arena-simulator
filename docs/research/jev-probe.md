# Jev 実 API プローブ（賭け判断）

`typesafe-ai/jev` を Vercel AI Gateway `/v1/evaluate` 経由で呼び、
賭け判断エージェント（`src/ai/JevBettingAgent.ts`）の設計に必要な性質を実測した記録。
調査用スクリプト（`scripts/probe-jev.ts`）は役目を終えて削除した（git 履歴に残る）。

- 実施日: 2026-09-23（UTC）、2 回に分けて実行（`--set=base` 20 回、`--set=v2 --budget=8` 5 回）
- 呼び出し: **合計 25 回**（上限 30 回。再試行も 1 回と数える設計だが再試行は発生しなかった）
- 観測値（能力値・オッズ）は実施時点で Battle Core が未接続だったため **概算の手組み**。実機データではない。
  よって「Jev の予想が正しいか」ではなく「Jev が与えた情報にどう反応するか」を見る調査である

## 1. レスポンス形式（実測）

```jsonc
{
  "model": "typesafe-ai/jev",
  "answers": {
    "winner": {                       // 質問キー（モデルには渡らない）
      "type": "choice",
      "choice": "3番 いっかくうさぎ",   // 最大確率の選択肢名
      "probabilities": {              // 選択肢名 → 確率。キー順は criteria 順ではない（毎回シャッフル）
        "1番 スライム": 0.04, "引き分け（勝ち残りなし）": 0.08, "3番 いっかくうさぎ": 0.79, "2番 おおがらす": 0.09
      },
      "confidence": 0.72
    }
  },
  "usage": { "inputTokens": 963, "outputTokens": 87 },
  "providerMetadata": {
    "typesafe": { "confidence": { "winner": 0.72 } },   // answers[].confidence と同値
    "gateway": {
      "routing": { ... },                                // 上流の試行履歴
      "cost": "0", "marketCost": "0.0000...", "surchargeCost": "0", "gatewayCost": "0",
      "generationId": "gen_..."
    }
  }
}
```

- 自由文（理由）は返らない。→ `BetDecision.reason` は確率から機械的に組み立て、その旨を明記する
- `choice` は 25 回すべて最大確率の選択肢と一致した。ただし実装は `probabilities` を正とし、`choice` は参考扱い
- `confidence` は分布が尖るほど高い（最大確率 0.98 → 0.98、0.42/0.40 の拮抗 → 0.21）。
  選手が拮抗しているかどうかの指標として meta に残す
- エラー本文は `{ "error": { "type", "message", "param" } }`
  - 無効キー: **401** `authentication_error: Authentication failed`
  - 以前の別プロジェクト実測: 503 `service_unavailable_error`、400 `AI_APICallError`（`max_tokens_exceeded`）、429（Retry-After ≈ 50 秒）
- `instructions` を省いた choice 質問も **200 で通った**（必須ではない模様）。ただし文言が判断を左右するので常に付ける

## 2. 確率の性質

| 観点 | 結果 |
| --- | --- |
| 合計 | 25 回すべて **ちょうど 1.00**（小数 2 桁丸め）。ただし丸めで 0.99/1.01 になりうるので正規化は残す |
| 再現性 | 同一入力の 2 回で差は最大 0.03。ほぼ決定的 → 同じ試合で呼び直しても情報は増えない |
| 0 の扱い | 0 は普通に返る（例: Analyst のスライム 0）。欠けた選択肢は無かった |

→ スキーマ（`src/ai/schemas/evaluateResponse.ts`）: 合計のずれ 0.2 までは正規化して `meta.normalized` に記録、
それ以上・未知の選択肢名・範囲外は不正として 1 回取り直す。

## 3. Classic / Analyst 差とオッズへの追従

M1 = スライム / おおがらす / いっかくうさぎ（手組みでいっかくうさぎが最も強い）。

| ケース | スライム | おおがらす | いっかくうさぎ | 引き分け | 確信度 |
| --- | --- | --- | --- | --- | --- |
| Classic（オッズ 5.2 / 3.1 / 1.8） | 0.04 | 0.09 | **0.79** | 0.08 | 0.72 |
| Classic・オッズなし | 0.14 | **0.56** | 0.19 | 0.11 | 0.42 |
| Classic・オッズ入替（1.8 / 3.1 / 5.2） | **0.42** | 0.37 | 0.08 | 0.13 | 0.22 |
| Analyst（オッズ 5.2 / 3.1 / 1.8） | 0.00 | 0.01 | **0.98** | 0.01 | 0.98 |
| Analyst・オッズ入替 | 0.00 | 0.04 | **0.95** | 0.01 | 0.93 |

- **Classic ではオッズに強く引きずられる。** 「倍率の高さは勝ちやすさの理由にならない」と書いても、
  低オッズ＝強い、として読む。名前だけ（オッズなし）では名前の知識で判断するが、いっかくうさぎを選ばない程度の精度
  - Classic で与えられる情報は名前とオッズだけなので、オッズを使うこと自体は合理的（格闘場のオッズは強さから決まる）。
    ただし Jev の分布はオッズの逆数（0.18 / 0.30 / 0.52）より極端で、**確率として較正されていない**
- **Analyst では能力値が支配的で、オッズの影響は小さい。**
  M3（はぐれメタル / メタルスライム / ドルイド）でもオッズ入替ではぐれメタル 0.37 → 0.28 程度の変化にとどまる
- M3 は Classic で はぐれメタル 0.42 / ドルイド 0.40 と拮抗（確信度 0.21〜0.22）、Analyst でドルイド 0.54〜0.59

→ オッズは state に含める（Classic で使える情報はこれだけのため）。期待値ベットは Jev の分布の較正に依存する（未解決事項 1）。

## 4. 同名モンスターの区別

選択肢名は「`番号` + 半角スペース + 名前」（`1番 アルミラージ`）で、state の各選手にも同じ `label` を持たせる。

| ケース | 1番 | 2番 | 3番 | 4番 | 引き分け |
| --- | --- | --- | --- | --- | --- |
| v1 アルミラージ×4 Classic（2 回） | 0.12〜0.14 | 0.01 | 0.01 | 0.01 | **0.83〜0.85** |
| v1 アルミラージ×4 Analyst（2 回） | 0.20〜0.22 | 0.01 | 0.01 | 0.01 | **0.75〜0.77** |
| v2 アルミラージ×4 Classic | 0.34 | 0.02 | 0.01 | 0.02 | 0.61 |
| v2 アルミラージ×4 Analyst | 0.43 | 0.03 | 0.01 | 0.02 | 0.51 |
| スライム×2 + いっかくうさぎ（v1 / v2） | 0.02 / 0.01 | 0.00 / 0.00 | **0.94 / 0.97** | — | 0.04 / 0.02 |

- 番号で選択肢自体は区別でき、別名が混ざる試合では正しく強い方を選ぶ
- しかし **完全に同一の選手どうしでは、1 番に確率が偏る（位置バイアス）**。観測が同じなら勝率も同じはず
- v1 の規則文「同じ名前の選手は番号だけが区別で、能力・行動は同じ」は **引き分けに 75〜85%** を寄せた。
  「同じ＝決着しない」と読まれたと考え、v2 で「同名でも別個体として互いに戦い、どれか 1 体が勝ち残りうる」に書き換えた。
  引き分けは 51〜61% に下がったが、位置バイアスは強まった

→ 対策:
1. **エージェントで対称化**（`symmetrizeIdentical`、既定 true）: id 以外の観測がすべて同じ選手どうしの勝率を平均する。
   位置バイアスの大きさは `meta.symmetryGap` に記録する
2. **プロンプトは v2 を採用**（`src/ai/prompt.ts` の `PROMPT_VERSION`）。同名以外の分布は v1 とほぼ同じ（M1 Classic 0.79 → 0.80、M3 Analyst 0.57 → 0.59）
3. 引き分けは選択肢に残す。選手しか選べないと、引き分けを予想したときの確率質量が
   選手に押し付けられて歪む。引き分けの払い戻しは誰に賭けても同じなので賭け先の比較には影響しない。
   `BetDecision.probabilities` は契約どおり引き分けを除いて再正規化し、引き分け確率は `meta.drawProbability` に残す。
   引き分けを外しても M1 Analyst では 0.98 → 0.99 と大差なし

## 5. エラー・レート制限・レイテンシ

| 項目 | 結果 |
| --- | --- |
| 成功率 | 24/24（無効キー試験を除く）。**5xx / 429 は 0 件**（この時間帯は混雑なし） |
| レイテンシ（1 試行の往復、n=25） | 最小 268 ms / 中央値 429 ms / p90 613 ms / 最大 994 ms |
| 入力トークン | Classic 約 870〜1,080、Analyst 約 1,290〜1,720（出力 69〜106） |
| 課金 | `cost` 合計 0（`marketCost` 合計 約 $0.0012） |

- 今回は 5xx が出なかったため、再試行経路の実測はできていない。設計は別プロジェクトの実測
  （503 が頻発、まとまると 429 と Retry-After ≈ 50 秒）とユーザー情報（5xx は Jev の人気による混雑）に基づく:
  - 5xx / 529 / timeout / network は一時障害として **最大 6 回、[300, 700, 1500, 3000, 6000] ms ± 30% ジッタ**
  - 429 は Retry-After を優先。10 秒を超える待ちはクライアント内で待たず `rate_limit`（`retryAfterMs` 付き）で返し、
    自動プレイのランナー（`src/ai/autoPlay.ts`）が AbortSignal を効かせたまま待つ（既定上限 120 秒）
  - 401/403/4xx は再試行しない。自動プレイも即停止する
  - UI 向け文言は「Jev が混雑しています。しばらく待って再試行してください」系にし、キーの問題と誤解させない
- 1 試合 1 呼び出しで 0.3〜1 秒なので、自動プレイ 1000 試合は混雑がなければ 7〜10 分程度の見込み

   Monte Carlo の勝率との比較・較正は Issue #24 で扱う（`scripts/compare-jev-mc.ts`）
2. **混雑時の挙動**: 今回 5xx が出なかった。混雑時間帯の 5xx 率・再試行後の成功率は未測定
